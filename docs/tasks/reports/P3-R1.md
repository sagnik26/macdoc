# P3-R1 report: red-team of the recipe catalog and detectors

**Scope:** `internal/recipes/redteam_test.go` only (no fixtures were needed, so there are no `testdata/r1_*` files). No implementation changes.
**Result:** 17 BUG tests fail and 10 held-up tests pass. All pre-existing tests pass (`go test -race ./internal/recipes -skip TestR1` ok). `make lint importcheck forbidcheck` is clean.

## Findings

Severity is my judgment: **High** means the safety model is bypassable by a catalog mistake. **Medium** means a real defect in the safety layer or a hang. **Low** means wrong numbers or a defense-in-depth gap that a later layer already catches.

## Attacks that held up (passing tests)

- **Argv lint** (`TestR1LintArgvHeld`): `system prune` adjacent to `--context`, `--volumes=true`, `--volumes` in `builder prune`, `rm` anywhere except `ollama rm` at `argv[1]` (`docker rm`, `docker image rm`, `docker container rm`, `ollama run rm`, `ollama list rm`, `brew rm`), `sh`, `bash`, `zsh`, `sudo` as arguments, `-rf`, two `{id}`s, `--x={id}`, backticks, `|`, `&`, `>`, newline, a non-tool `argv[0]` (`/bin/rm`, `./brew`, `Brew`, `env`, `sudo`).
- **Pattern lint** (`TestR1LintPatternHeld`): `~/*`, `~/**`, `~/**/*`, `~/**/node_modules`, `~/*/**`, `~/**/**/x`, `.` and `..` components, `//`, a trailing `/`, absolute paths, `~user`, `~`, a bad glob, relative and empty patterns.
- **simctl** (`TestR1SimctlHostileIdentifiersHeld`): runtime keys or identifiers `--all`, `-rf`, `a b`, `../x`, `x/y`, `x\ny`, `$(id)`, `x;y`, 300 characters and empty never become a NativeArg. A key/identifier mismatch, a missing or false `deletable`, and `null` entries are skipped. Hostile device UDIDs never become a NativeArg for `sim_devices_idle`. Note that a runtime keyed and identified as `all` passes `validNativeArg` and is emitted, which would produce `xcrun simctl runtime delete all` (see ambiguity 5).
- **ollama** (`TestR1OllamaHostileNamesHeld`): `-rf`, `--help`, `x;y`, `$(id)`, backticks, `../x`, `hf.co/…`, `\r`, NUL and a 100 KB name are all rejected by `ollamaNameRe`. `a b` can't occur, because ollama names have no spaces, and `strings.Fields` would only take `a`.
- **docker df** (`TestR1DockerMalformedHeld`): `-1GB`, `NaN`, `1e9B`, empty, `1.2.3GB`, `1PB` and non-JSON give an error, never a negative or a silent 0.
- **brew**: the `PB` unit and a missing summary give `SourceUnknown` with a reason, never 0 (in `TestR1BrewAbsurdSize`).
- **nvm** (`TestR1NvmHostileAliasesHeld`): an alias loop, `../..`, an absolute path, empty, `lts/*` and `system` all emit nothing. A symlinked alias file is only read, and both the default and the newest are kept.
- **AVD names and sysdir** (`TestR1AVDHostileInputsHeld`): `-n`, `--all`, `a b`, `x;id`, `$(id)`, `..` and a tab are rejected by `validNativeArg`. `image.sysdir.1=../../../../` doesn't crash and only marks more images as used (fail-safe).
- **Version ordering** (`TestR1VersionOrderingHeld`): DeviceSupport `10.0` > `9.9`, `iPhone15,2 10.0.1`, `18.0 beta`, non-numeric names and files. build-tools `10.0.0` > `9.0.0`, and `35.0.0-rc1` and `latest` are never emitted or treated as newest. Gradle `8.10` > `8.9`, and `-rc-1` is never emitted. The newest is never emitted.
- **Symlink tricks** (`TestR1NodeVenvSymlinkTricksHeld`): symlinked `package.json`, lockfile, `pyproject.toml` and `pyvenv.cfg` don't count. A symlinked project directory makes the detector emit (it Lstats through the parent), but `CheckTarget` canonicalizes it into `~/Documents` and drops it.
- **Side effects** (`TestR1DetectorSideEffectsHeld`): I ran every catalog detector against `fstree.DevHome` with every tool "installed", with real fixtures and then with an always-failing runner. The only commands run were from the read-only set (`brew cleanup -n --prune=all`, `brew autoremove -n`, `docker system df …`, `docker images -f dangling=true …`, `xcrun simctl list -j devices`, `xcrun simctl runtime list -j`, `xcrun --find simctl`, `tmutil listlocalsnapshots /`, `conda clean --all --dry-run`, `ollama list`). npm, pnpm, yarn, npx and corepack never ran, and the home tree was byte-identical afterwards (paths, modes, sizes, mtimes). No detector touches the network except through those commands. (R1-03 is the caveat: the dry-run argv comes from the recipe, not from code.)
- **Robustness** (`TestR1RobustnessHeld`): I ran every detector with four NodeSources (erroring, nil, unsorted junk with empty and relative paths, negative or MaxInt64 sizes and mtimes, and 20,000 nodes) and four runner outputs (empty, binary junk, 50,000-line, and `null`). There were no panics.

## Judgment on the riskiest quarantine patterns

- **`~/Downloads/*` (`user.downloads_large_old`, CAUTION, 90 days, ≥ 500 MB, files only).** Quarantine is reversible, CAUTION is excluded from `--safe`, and confirmation is typed, so it is acceptable for v1. **But** `restore.kind: redownload` is not honest for every match. AirDrop and iPhone imports land in `~/Downloads`, and a 600 MB+ video from a phone may be the only copy. Recommendations: set restore kind to `irreplaceable`-style wording in the note ("may be the only copy"), or restrict matches to installer and archive extensions (`.dmg .pkg .xip .zip .iso .tar.* .ipa .apk`) and make anything else advise-only. Also make sure quarantine purge never auto-expires these items.
- **`~/Library/Caches/*` (`user.app_caches`, CAUTION, ≥ 500 MB).** These are mostly regenerable, but there are three concerns. (1) **No `stale_days`**, so caches in use today are emitted. (2) **No `app_not_running` precondition**, because the owner is unknown, so a cache can be moved from under a running Chrome or Slack. (3) Some apps keep real state in Caches. JetBrains IDEs keep **Local History** under `~/Library/Caches/JetBrains/<IDE>/LocalHistory`, which is unrecoverable edit history. Recommendations: add stale_days (e.g. 14) and exclude `JetBrains` and `Google` (R1-10). Keep it CAUTION.
- **`~/*/**/node_modules` (`node.node_modules_stale`, CAUTION, 90 days, ≥ 50 MB, needs package.json and a lockfile).** A vendored, committed `node_modules` usually *also* has a lockfile, so the lockfile rule doesn't exclude it. However, committed means it is restorable from git as well as from quarantine, and patch-package edits are reapplied on install. This is acceptable. Residual risks: `npm link`-ed packages (symlinks are moved, not followed, so they're fine) and locally hand-edited modules. Consider the existing `git_clean` precondition or a "tracked by git" downgrade to advise in Phase 4. R1-11 (protected folders) applies.
- **`~/*/**/.venv` (`python.venv_stale`, CAUTION, 90 days, needs pyvenv.cfg and a project marker).** SAFETY_MODEL §2 lists *"venvs with local edits"* as **RISKY**, but the recipe is CAUTION. An editable install (`pip install -e`) lives in the project, not the venv, so it's fine. Packages patched in place inside `site-packages` are lost on rebuild. The restore cost is a full `pip install`, which may not reproduce the environment if there's no lockfile (`requirements.txt` without pins). I recommend RISKY, or CAUTION only when a lock (`uv.lock`, `poetry.lock`, pinned requirements) exists. Needs a tech-lead decision.
- **`~/Library/Logs/*` (`user.logs`, SAFE, 30 days via the classifier, restore none).** These are low value, and SAFE is fine. Caveats: (1) `children` doesn't filter staleness. That relies on the P3-W3 classifier, which keeps findings whose idle time is **unknown** (MtimeMax 0). A Logs child with an unknown mtime would be SAFE-cleaned regardless of age. (2) `DiagnosticReports` holds crash reports a developer may want for a bug in progress, which is acceptable at 30 days. (3) It overlaps Android Studio logs (R1-10).

## Spec ambiguities

1. **Is the lint meant to be an allow-list?** SAFETY_MODEL §5 implies it ("recipes pin exact argv"), but `lintArgv` is a deny-list. R1-01, R1-02 and R1-05 all follow from this.
2. **Should `lintPattern` enforce protected paths** (SAFETY_MODEL §5 says so), or is runtime `CheckTarget` enough? R1-04.
3. **Unknown idle time vs. `stale_days`.** P3-W3 drops a finding only if idle days are *known* and below StaleDays. So ollama models with relative MODIFIED dates, and `children` nodes with MtimeMax 0, bypass staleness entirely. Should unknown idle time count as "not stale" for CAUTION recipes, as `stale()` and `idleFor()` already do inside detectors?
4. **Native finding targets are informational, but who validates them?** `android.avd` (R1-06) and `xcode.sim_runtimes` take a directory from the tool or registry, and the native tool deletes that directory. The P3-W1 answer ("executor re-validates NativeArg against a fresh listing") doesn't help when the listing itself points somewhere wrong.
5. **`xcode.sim_runtimes` emits the newest runtime per platform** (with a note), and an identifier of `all` passes `validNativeArg`. Should the newest be advise-only? Should `all` and other tool keywords be rejected as NativeArgs?
6. **`stale()` vs `idleFor()`.** With a zero `Env.Now`, the W2 detectors treat nothing as stale, while W1 falls back to the wall clock. This is harmless but inconsistent. The contract should say whether `Env.Now` is required.
7. **`python.venv_stale` risk class:** CAUTION in the catalog vs. RISKY in SAFETY_MODEL §2 (see above).
8. **`docker.unused_images` ⊇ `docker.dangling_images`**, and `docker.build_cache` comes from the same df. The classifier should de-duplicate (raised as P3-W2 Q4 and answered as "classifier"). I mention it again because R1-10 is the same class of problem for quarantine items.
